# Neutral Challenge: Read-Only Tool Deadlines

The parallel-wave design adds an optional timeout configuration to the exported `AssistantServerConfig`. This is a public package API change even though it is additive. Challenge the necessity and safety of that choice before implementation.

1. **Why not a fixed internal timeout?** It avoids a public option and is easier to test, but a large repository may need a different deadline. A fixed value also leaves embedded hosts unable to tune their runtime without patching Turnturn.
2. **Why not a model-supplied `timeoutMs` on every tool?** It puts resource control in an untrusted caller's hands and changes tool schemas. A host-owned maximum would still be required. The current shell tool already accepts `timeoutMs`; that is not precedent for allowing unbounded read/search timeouts.
3. **Why not put the deadline in `ToolWaveRunner`?** The runner could enforce every wave's wait centrally, but would need host configuration threaded through public engine options or would hardcode a value. A decorator behind the existing `ToolExecutorPort` lets the server configure time limits while the core scheduler stays provider- and host-neutral. The cost is that a different host must compose the decorator too; the core port alone cannot promise bounded arbitrary executors.
4. **Can logical timeout lie about effects?** Yes for mutating tools. A `Promise.race` can say a write failed while it later changes a file. This change must limit synthetic deadlines to admitted read-only built-ins, keep writes/edits sequential, and state that physical interruption of an ignored abort signal is not guaranteed.
5. **Can late callbacks leak after timeout?** The wrapper must gate both the returned outcome and callbacks, and tests must force a late callback/resolution. A read that keeps consuming filesystem resources after logical timeout remains a resource concern, so built-ins should cooperate with abort during traversal and reading.
6. **Does the optional configuration need a durable record?** The record contract already captures each request and terminal result. A timeout becomes a failed result with a stable code; no new record type is needed. The configured threshold is operational context, not session replay input, though trace metadata should identify the effective deadline for diagnosis without altering durable protocol.

If implementation shows the existing `ToolExecutorPort` cannot preserve exactly one outcome or a server-only decorator cannot cover both memory and persistent runtimes, stop and revisit the design instead of widening the public core API informally.
